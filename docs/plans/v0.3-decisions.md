# v0.3 decisions

The contract for the v0.3 renderer and v0.3.1 themes. Every ticket session reads it first. Each section below is marked:

- **agreed**: the user decided it in the planning interview (2026-10-18).
- **research**: research changed or refined it (2026-10-19, findings in the conductor's notes).
- **ticket**: a ticket session decided it; logged under [Ticket log](#ticket-log).

When a ticket needs to change anything here that affects the outcome for the user (a feature, a behaviour, a look, a limit), it says so in its report. It doesn't quietly diverge.

## Goals (agreed)

- v0.3 is the foundation for v0.4's UI: animated carousels, metadata screens, and RetroArch-style views. It is built for speed, responsiveness and functionality, and it can be customised deeply in code.
- The menu keeps today's screens, flow and keys. They are drawn as tiles with the new proportional fonts, in a flat default theme with light and dark variants and accent colours. The 16bpp background pictures go.
- v0.3.1 adds themes from SD (`themes/<name>/theme.ini` plus LZ77 assets), a PNG converter, and `just theme-check`.

## Engine

### Frame (agreed + research)

- A fixed 60 fps loop. Each frame wakes from `VBlankIntrWait`, then:
  1. commits the previous frame's shadow state in VBlank;
  2. reads input;
  3. updates motion;
  4. runs jobs for the rest of the budget;
  5. draws.
- The phases stay separate. Draw never touches hardware registers, and commit never calls widget code.
- The engine's IRQ handler runs from IWRAM, sets `REG_IFBIOS` and counts VBlanks. Motion advances by `dt` = VBlanks since the last frame, clamped to 3.
- When idle (no motion, no job, no input, nothing dirty), the loop skips draw and commit and only halts. Dirty flags are kept per shadow region.
- **Jobs:** slow work runs as state-machine jobs (a function plus a state struct, as in pokeemerald's tasks).
  - The frame has a cycle budget, timed with the TM2/TM3 cascade that Diagnostics already uses.
  - At least one job step runs per frame.
  - One step is at most one SD command (2 KB), `f_read` of 2–8 KB with the `FIL` kept between frames, `f_readdir` of N entries, or one LZ77 cover.
- Any IRQ that can run during an SD transfer runs from IWRAM only, because the SD path switches to the slow WAITCNT.
- **Targets:** input reaches the screen within 1 frame, scrolling never drops a frame, and switching screens takes under 100 ms, not counting SD reads.

### Text (agreed + research)

- Glyphs are drawn straight into VRAM BG tiles by an ARM blitter in IWRAM, with no RAM window buffer.
  - It does a 16/32-bit read-modify-write, never byte writes.
  - Window tiles are in column-major order.
  - Masks are loaded from a global (check the GCC 10 output).
  - Each word is written once.
- Text uses palette-index colours, so theming is a palette change and nothing is redrawn.
- **Lists aren't double-buffered.** New rows are drawn off-screen in the wrapping 32x32 map, 1–2 rows ahead of the scroll.
- Two tile sets, swapped by map in VBlank, are used only for small windows that change in place: the status line, and a marquee if one is ever added.
- **List rows are 16 px** (a multiple of 8), so a row never shares a tile row with its neighbour. Today's rows are 14 px. *(research; affects the look: about one row fewer per screen.)*
- **Selection** is shown by switching the palette bank in the row's map entries, or by a sprite or window highlight. It never redraws text.
- **Whole-page changes** (a folder change or a page jump, about 760 glyphs, about 1.7 frames) are drawn while hidden and shown in VBlank, so half-drawn text never appears.
- Names are cut and measured by UTF-8 character through `charset_next()`. A name too long for its row ends in an ellipsis.
- Full names of any length are kept outside EWRAM (for example a PSRAM index), so names over 99 bytes list, open, launch and save (ticket T9).

### Views and widgets (agreed + research)

- **Nodes:** a flat static pool of nodes (24–32, u8 links, in EWRAM), with an arena per view: push bumps a high-water mark and pop resets it.
- **Ops:** each widget kind has a `const WidgetOps {measure, event, update, draw}` table in ROM.
- **Kinds:** label, list, grid, image, panel, scroll bar, progress bar.
- **Layouts:** a layout is a `const ViewSpec` array in ROM, with fixed rectangles and anchors (left, right, fill) and no layout pass.
- **View stack:** push and pop, for dialogs and overlays. The view below stays resident but isn't drawn unless it is visible under the top one.
- **Focus:** one focus per view, and the top view is modal.
- **Data:** lists and grids draw from a `ListModel {count, fetch(i, &ItemView), prefetch(lo, hi)}`. The widget owns only its scroll position, its cursor, and K = visible + 2 row slots, so 10 items and 10,000 cost the same. A carousel in v0.4 is another widget on the same model. `fetch` never calls FatFs or switches the ROM page while a commit is pending; slow data comes through `prefetch` and jobs.
- **Invalidation:** a dirty bit per node, plus a dirty-row mask per window (u32). There is no rectangle merging.
- **Caps:** nodes, windows, views and motions have explicit caps, and hitting one gives a readable error.
- **IWRAM** holds only the blitter, the IRQ handler and the commit path. Everything else runs from ROM.

### Motion (agreed + research)

- **Eased tweens** have a fixed duration and a 256-entry easing table. They drive fades and fixed transitions.
- **Springs** are critically damped (s32 16.16, semi-implicit Euler). They drive anything the user can interrupt: list scroll, cursor, panel slides. A spring keeps its velocity when its target changes, so a press during motion retargets it with no hitch and never queues. *(research: replaces "retarget the tween".)*
- **Properties:** motion can drive BG scroll, sprite position, scale and rotation (affine), palette fades (the faded buffer is rebuilt from the unfaded one in update and copied in VBlank), and blend alpha.
- **HBlank:** no HBlank IRQs. If a per-line effect is ever needed, it uses HBlank DMA from a table.

### Input (agreed + research)

- Repeat state is kept per key, counted at 60 Hz. It doesn't use libgba's shared `setRepeat`.
- A tap acts on the frame it is pressed.
- Holding repeats after 15 frames, then every 4 frames, every 2 after about 1 s, and every frame once the scroll animation is skipped at that speed.
- Speed-up resets on release or a change of direction.
- L and R page, on their own schedule: 20 frames' delay, then every 8, with no speed-up.
- Wrapping at a list end happens only on a fresh press, or after a 10–20 frame pause at the end. A repeat never wraps.
- All timings are layout and theme data.

### Resources (agreed + research)

- **Allocators:** there are allocators for BG character and map blocks, sprite tiles, palette banks (tagged, as in pokeemerald) and affine matrices (32).
  - A view owns what it allocates.
  - A freed item is ref-counted and its removal deferred (Butano style), so showing it again is free.
  - Free neighbours merge when space is reclaimed.
- **OAM:** a shadow OAM and affine buffer, built behind a guard and copied in VBlank. Unused entries are hidden explicitly.
- **Commit queue:** one VBlank commit queue, capped by bytes and by VCOUNT. Work left over waits for the next frame.
- **Budget checker:** checks each layout, up front, against VRAM, both palettes, sprite tiles, affine matrices and PSRAM bytes. A layout over budget is rejected with a readable error.
- **Covers:**
  - Covers are cached decoded (raw 8bpp tiles) in PSRAM, read through the `0x08800000` window from normal kernel code, all within one 8 MB page. `SetPSRampage` is slow, so it runs once per batch. *(research: replaces the IWRAM, IRQs-off route.)*
  - The route is SD, then a word-aligned staging buffer, then BIOS LZ77, then PSRAM. PSRAM is written at the slow WAITCNT until writes at `WAITCNT_MENU` are confirmed on the cart.
  - DMA3 copies 1–2 covers into sprite slots per VBlank.
  - Covers are evicted by distance from the cursor, and neighbours are prefetched first.
  - The cache is empty after each game launch.

### libtonc (agreed + research)

libtonc isn't linked, because its headers clash with libgba. Routines worth having are copied into `source/engine/` and credited: the chr4c blitter design, `memcpy32`/`memset32`, and the sine and division tables. Each is kept only where the cycle test shows it is faster than our own.

## Fonts (agreed)

Two proportional 1bpp fonts with width tables: body text on a 12 px line and headings at 16 px, covering Latin-1. They are converted by `tools/font.py` and credited in About. The user picks them from a preview sheet (ticket T1).

## Testing (agreed + research)

- **Goldens:**
  - The gate is a hash manifest, `tests/shots/hashes.txt` (from mgba-shot `-h`). PNGs are committed for review.
  - Comparison is exact. On a mismatch the test writes a PNG and a diff image to `dist/shots-failed/`, which CI uploads.
  - `just shots-update` re-records the shots and prints what changed.
  - Each scenario is an mgba-shot `-i` file that waits on `tlog("screen ready: NAME")` rather than on fixed frames.
  - An animation is checked by hashing every frame, with PNGs only for key frames.
  - The clock and blinking are masked or pinned. Scenarios are few and targeted, not every combination.
- **Cycle budget:**
  - Counted in the ROM with cascaded timers (both enable bits set), logged as `frame-cycles: SCREEN N`, and checked against `tests/perf/budget.txt`.
  - It fails at 280,896 cycles per frame, or when a figure drifts more than 10% above its recorded value.
  - IRQs inside a measured section are accounted for.
- **On the cart:** Diagnostics gets a renderer step. It times the glyph, the scroll step, an LZ77 cover, a PSRAM copy and a PSRAM write with the same timer code, flags any figure more than 20% above the emulator's, and shows a 10-second scroll-and-fade demo for watching for tearing.
- Hardware-free engine code (motion, input, list maths, layout and budget checks, theme parsing) gets host tests under ASan and UBSan.

## Other (agreed)

- A DIM setting, off by default, lowers the screen's brightness through the blend registers after N idle minutes.
- The port goes screen by screen: the engine lands first. Mode 3 and `draw.c` are deleted before v0.3 is tagged.
- Commits are unsigned while 1Password signing is unavailable (`git -c commit.gpgsign=false commit`).

### T5 Motion and input (merged)

- **Feel (contestable):**
  - Wrapping: a held key wraps once the cursor has rested at the list end for 15 frames (`wrap_pause`); a repeat arriving sooner never wraps. "A repeat never wraps" above is read that way.
  - The first fast repeat comes when a 4-frame repeat would fall at or past 60 frames held: a held d-pad fires on frames 0, 15, 19 ... 59, 61, 63 ... The every-frame repeat applies only past that point, when the caller says the animation is skipped.
  - Pressing a new direction restarts the schedule of every held direction; L and R don't. Keys other than the d-pad, L and R fire only on the press.
  - Springs take 4 semi-implicit Euler steps a frame (stable up to omega 1.875 rad/frame), and dt 3 lands exactly where three frames of dt 1 do. Presets: `SPRING_FAST` 1.0 (90% of a jump in 4 frames), `SPRING_SCROLL` 0.75 (6), `SPRING_GENTLE` 0.5 (8). A spring settles within 1/16 of its target's step and then snaps.
  - Motion values are 16.16 and must stay within +-16384 units: a list taller than that scrolls a window-relative spring and rebases it with `motion_spring_shift`.
  - The motion pool holds 16 (`MOTION_CAP`), about 0.6 KB of EWRAM.
- **Follow-ups for T6** (review nits): compute the spring offset in int64 at the value limits; check the range before allocating a motion; round palette fades symmetrically; restart held directions on release, as the contract says (or document that they don't); add a fade-factor target kind or a header note on 16.16 setter values.

### T3 Test setup (merged 04dc6d2, clock fix 082122b)

- **Screen-ready markers** log at debug level (`tlog_debug`), so a card's log at INFO doesn't fill with them. A `file-menu` marker was added for the cheats scenario.
- **Clock:** goldens run with the clock frozen at 2026-01-01 12:34:56 UTC (mgba-shot `-C`, added by the conductor after review). T3 had only pinned the start, so a golden could change by one second.

Scenarios navigate by fixed key presses (for example R×3, DOWN×4 for DIAGNOSE). A port that reorders settings re-records with `just shots-update` and keeps the `screen ready` names.
- **Thin animation failures:** a failing animation frame gives only the actual PNG, with no expected PNG or diff.
- **Kernel bugs found (pre-existing, cosmetic):** listed under v0.3.2 in the roadmap. The ports should fix them.


### T2 Engine core (merged 9558a68, review fixes 79a3a67)

- **IRQ:** the engine adds no IRQ handler. The kernel's `torii_irq` (`source/crash.s`) and libgba's `IntrMain`, both in IWRAM, already count VBlanks (`torii_frames`) and set `REG_IFBIOS`, so a VBlank during an SD transfer stays safe. A handler in `IntrTable` would run from ROM, so none may be added.
- **Commit:** `frame_begin` commits in the main loop right after `VBlankIntrWait`, not inside the IRQ. Only the queue loop (`gfx_commit_queue`, 232 bytes) is in IWRAM. The register, palette and OAM part is a few writes and DMA starts, and runs from ROM, saving about 400 bytes of IWRAM.
- **Commit caps:** 16 KB per frame, no chunk starts at or after line 225, 1 KB chunks, 16 queue entries. `gfx_hold_for_queue` keeps chosen register regions back until the queue drains, so a page flip never shows a half-drawn page.
- **Cycle counter:** TM2/TM3 run free from the first use, and every timing is a difference. Diagnostics' timer uses the same counter. A game launch stops the timers (`RegisterRamReset` with `RESET_OTHER`).
- **Allocator units:**
  - BG VRAM is 2048 units of 32 bytes. Maps come from the top and tiles from the bottom, within the 1024 tiles their charblock reaches.
  - Sprite VRAM is 1024 units of 32 bytes.
  - BG and sprite palettes are 16 banks each.
  - There are 32 affine matrices.
  - Block slots: 24 each for BG and sprite VRAM.
- **Ownership:** a LIFO allocation log (`res_mark` / `res_release_to`, 48 entries) is the per-view arena.
  - Tagged blocks dropped to zero references stay cached. They are reclaimed oldest first, only when space runs out.
  - Untagged blocks are freed at once.
  - `res_fresh()` tells a new block from a shared or revived one, so a caller uploads only into a new block.
- **Idle:** setters and OAM rebuilds mark a region dirty only when it really changes. `frame_wake()` lasts until `frame_end`, and a job that finishes wakes the frame.
- **Budget:** the checker compares totals, with cached blocks counted as free, so fragmentation can still fail an allocation. PSRAM defaults to 8 MB (`budget_psram_bytes`); T7 may lower it.
- **Memory:** the engine uses about 4.6 KB of EWRAM, leaving about 2.3 KB free, and 336 bytes of IWRAM, leaving 3668 bytes free. The 1 KB faded palette and the 1 KB shadow OAM are required by this contract. T4 to T7 have little EWRAM left. T9's PSRAM name index could free `pFilename_buffer` (52 KB).
- **Conductor review fixes:** the VRAM queue's bounds check could overflow and let a copy reach cart SRAM; the timer check is now exact; a note in jobs.h that `JOB_CANCEL` replaces the state; the smoke scene logs at debug level.
- **Open for T6:** while the queue drains over several frames, draw runs again, so draw must be idempotent. A hold on a clean region stays until that region is next written.


### T4 Text (branch v03-text)

- **Generated fonts are committed** in `source/engine/font_body.c` and `font_heading.c`. `just font` writes them, and `tests/font_test.py` fails when they no longer match their BDFs and options. Generating them at build time would need Python in the devkitARM container (it has none) and the BDFs in `just repro`'s copy of the source. They are in `.clang-format-ignore`, as the test compares font.py's output byte for byte.
- **Rows are always 2 bytes** (font.py writes no 1- or 4-byte rows; glyphs are at most 16 px). Galmuri9's 9 px glyphs (© ® ¼ ½ ¾, the replacement glyph) keep their shapes. Measured: the blitter reads an 8 px glyph's row as one byte at either row size, so a 38-glyph body row costs 9483 cycles both ways; 1-byte rows would only save about 1.5 KB of ROM.
- **The blitter is ARM assembly** (`source/engine/text_blit.s`, 556 bytes of IWRAM). GCC 10 at -Os spilled the 0x01010101 mask inside the loops even when it was loaded from another file's global. In ARM code a shift by a register holding 32 gives 0, so the wide loop needs no case for x on a tile boundary. Timed in mGBA at WAITCNT_MENU against the same design in C and a C port of libtonc's chr4c_drawg_b1cts_fast (both kept in `tests/kernel/text_bench.iwram.c`, test kernel only):

  | | 38-glyph body row | per glyph | 20-glyph heading |
  |---|---|---|---|
  | asm (kept) | 9491 | 249 | 8465 |
  | same design in C | 11649 | 307 | 8785 |
  | libtonc design, C port | 19015 | 500 | 14452 |

  A whole page of 760 glyphs is about 190,000 cycles, 0.68 frame (the plan estimated 1.7).
- **Each tile word is written once per glyph row.** The libtonc design writes the middle words of wide glyphs twice.
- **Text API** (`source/engine/text.h`): a window is any tile pointer with a width and height in tiles, in column-major order. `text_draw` takes UTF-8 and a clip width and returns the pen. `text_layout` and `text_draw_line` lay out once and draw later. `text_width` gives the pen advance, `text_line_fits` checks a line against a window, and `text_clear` / `text_clear_rows` fill opaquely with a palette index. A line must fit the window's height, or nothing is drawn and an assert is logged.
- **The ellipsis is "..." (contestable):** the fonts are Latin-1, which has no U+2026. It is 10 px in the body font. Spaces before the cut are dropped, and if not even "..." fits, nothing is drawn.
- **Characters outside Latin-1 draw the replacement glyph** (Galmuri's boxed "?") instead of '?'. Latin Extended-A letters still lose their accents, and dashes and curly quotes still become ASCII. This affects the look once screens are ported.
- **text_clear runs from ROM.** A clear of the window's full height is one CpuFastSet: 1671 cycles for 30 x 2 tiles. An 8 px row of 30 tiles in a taller window takes about 3540 cycles.
- **IWRAM is tight:** 3100 bytes are free after T2 and T4, against `just stack`'s deepest chain of 2632 bytes, a margin of under 500 bytes. T6 and later should add nothing to IWRAM without freeing some. Turning wide glyphs into two narrow passes would save about 160 bytes, but would write middle words twice.
- **Demo:** with L held at boot (`mgba-shot ezkerneltest.gba -k 1:L`), the test kernel draws a mode 0 text sample after its tests instead of the engine's scene (`tests/kernel/text_demo.c`). T6 replaces it.
- **Follow-ups for T6** (from review):
  - A list should use one `text_window` per 16 px row (30x2 tiles), not one ring window 32 tiles high. At 30 columns, that ring window would take 960 of a BG's 1024 tiles.
  - There is no left clip or start pixel, so a marquee would need one.
  - A `struct text_line` is about 145 bytes: keep lines on the stack, not one per row.
  - U+00AD draws as a visible hyphen.
- **Conductor review (T4):** approved. Follow-ups for T6:
  - Add a left clip or start offset to the text API, and lift the 128-glyph `text_line` limit, for marquees of long names.
  - Treat any IWRAM growth as a hard gate (about 470 bytes of margin over the deepest stack).


### T16 EWRAM (ticket)

- **Result:** EWRAM free goes from 2316 to 20136 bytes (`just size`), with no change to what the user sees. IWRAM is unchanged.
- **`pReadCache` is a scratch buffer.** It holds nothing between two passes of a menu loop: each owner borrows it for one operation. The owners and their offsets are listed in `source/ez_define.h`, and new ones go there.
  - Mode 3's `Vcache` aliases its first 75 KB, but nothing draws there: every draw call passes `isDrawDirect = 1`. Only `Clear()`'s fill line, `[0, 0x1E0)`, is written on every draw.
  - While the menu is idle, T7 may use it as staging, as long as it is done before one of the listed operations starts. Those are: listing a folder (the sort's work at `0x800`), a thumbnail (`[0x10000, 0x14B38)`), the cheat screen, a launch, a NOR write, save backup or restore, and Diagnostics. `[0x14B38, 0x20000)` is touched by none of the menu-time owners.
- **Moved into `pReadCache`:** the cheat screen's line and value buffers (`buf` and `_paramv`, 12 KB, now its last bytes), `sort_by_name`'s work buffer (2.1 KB; the caller now passes it in), and `test_cheat_cap`'s line (2 KB).
- **Right-sized:** Recently Played rows go from 512 to 356 bytes. That is the longest entry `get_count` keeps or the kernel writes: a folder under `MAX_path_len`, a `/`, and a 99-byte name. This saves 1.5 KB.
- **Cheat list cap (contestable):** a cheat file now lists at most 2053 lines (sections plus entries), so the list can't reach the borrowed buffers. Lines past the cap are left out and logged; a line that adds both a section and an entry (`a=b[c]`) can't pass it either (review fix `664670e`). Before, the list had no cap: past 2275 lines it ran off `pReadCache` into `pNorFS`.
- **Left alone:**
  - `pFilename_buffer` and `pFolder` wait for T9's PSRAM index. The launch path keeps pointers into them while `pReadCache` is overwritten, so they can't share it.
  - `pNorFS`, `pCHEAT` (it must survive the game's load), the log ring, the crash block, and `SET_info_buffer` and `FAT_table_buffer` (both used next to NOR writes or a launch) stay.
  - The 128 KB chunk size stays: NOR erase blocks and the patchers work in 128 KB blocks.
- **Bugs found (pre-existing):**
  - The cheat list overran `pReadCache` past 2275 lines (fixed by the cap).
  - `Get_KEY_val` `strcpy`s a 50-byte key value that may lack its NUL.
  - `Get_CHT_val` compares a 50-byte `_paramk` that may lack its NUL.
- **Conductor review (T16):** approved. EWRAM is 20,136 bytes free after the merge with T4. The cheat-file cap is a behaviour change, called out under Decisions. A pre-existing Diagnostics quirk: `step_loader` reads the loader title after `say()` has cleared part of `pReadCache`, so the logged title can be garbled. Tracked in v0.3.2.

### T6 Views and widgets (branch v03-ui)

- **Where:** `source/ui/`. `ui.h` is the API screens use; `ui_core.c` (node pool, view stack and arena, layouts, patches, focus, key dispatch), `ui_ring.c` (list maths) and `ui_theme.c` are hardware-free and host-tested; `ui_run.c` (frame loop, planes, windows, blending, VRAM staging, fades, DIM), `ui_widgets.c` and `ui_list.c` are kernel-only. No IWRAM code; EWRAM +1816 bytes (24 nodes of 16 bytes, 4 views, a 448-byte widget arena, the input state, the staging table): 17,096 bytes free after T7.
- **How a screen is written:** a `const struct ui_spec[]` (kind, id, parent, plane, anchor, flags, ink and paper roles, x/y/w/h, a kind config) and a `const struct ui_view_spec` (name, nodes, id, first focus, flags, an event handler). `ui_push(&spec, ctx)` shows it on top of the stack; `ui_frame()` runs one frame (commit, input, motion, update, jobs, draw); `ui_pop()` releases everything the view took (nodes, arena, `res_release_to`, `motion_free_owner`, `jobs_cancel_owner`). The handler gets keys no widget took (`UI_EV_KEYS`) and widget events (`UI_EV_ACTIVATE`, `UI_EV_CURSOR`); a pop from inside it waits for the end of the event phase. Lists take a `ui_list_model {count, fetch, prefetch}` with the view's ctx; `ui_list_reset` (new content, a page change) and `ui_list_refresh` (items loaded) are how a model's job reports back.
- **Ops:** `WidgetOps` is `struct ui_ops {state_size, measure, init, event, update, draw}`: `init` is added to the contract's four, to take tiles and motions at push after `measure` has passed the budget check. `measure` gets the laid-out node, so anchored sizes are known.
- **Planes (contestable):** a widget names one of the four BGs. Within a view a lower plane number is in front; a pushed view is in front of the views under it (BG priority by depth), which stay resident and show only on planes it doesn't use. A list or grid needs a plane of its own (it scrolls it) and one of the two hardware windows (to clip its ring map to its rectangle), so at most two lists are resident at once. Planes 1 and 3 take tiles from character blocks 1 and 2, planes 0 and 2 from block 0. Rectangles are whole tiles.
- **Map changes on screen go through a VRAM staging area:** one 2 KB screenblock. A widget gets whole map rows copied there (VRAM to VRAM), changes them, and the commit queue copies them back in VBlank, so a selection change or a label flip shows in one frame and costs no EWRAM. The area is reused only once the queue is empty; full means "try next frame". Maps of a view not shown yet, and ring rows not on screen, are written directly.
- **The list's ring:** rows are 16 or 32 px; slots K = visible + 2, where visible is the most rows partly on screen ((h - 1) / rh + 2: 11 slots for a 128 px list, 30 x 2 tiles each as T4 advised). Row r draws into slot r % K and map rows (r % ring rows); a host test scrolls at random for 100,000 frames and checks a row never lands in a slot or map row on screen. For that the shown scroll moves at most one row a frame (`ring_step`): the spring may run ahead and the list catches up at 16 px a frame (a page with L/R takes 8 frames, smooth). The spring is window-relative and rebased past 2048 px (`ring_rebase`, `motion_spring_shift`), so 65,535 rows scroll. Fast repeat (the T5 skip flag) jumps the scroll instead of animating it.
- **Selection** is a palette bank switch of the row's (or grid cell's) map entries: bank 1 maps BG and PANEL to the selection colour and TEXT to the selection text colour, so the row's paper becomes the highlight. Text is never redrawn for it.
- **Page changes (contestable, affects the look):** a jump further than visible + 1 rows (a new folder, a wrap from the end to the start, `ui_list_reset`) hides the list's plane at the next commit, draws the rows the frame after (spread over frames within a cycle budget, as a new view's first draw is), and shows the plane in the VBlank after that. The list area is blank for one or two frames (17-33 ms). Double-buffering the slots would need twice the tiles (over 1024 for a full-width list), so this is the contract's "drawn while hidden".
- **A refresh of a row on screen (data arriving for a pending item) redraws it in place** and can tear for one frame; pending rows draw blank until then.
- **Marquee (decision, pixel unit):** `text_layout_window(font, s, len, skip, clip, line, &lead)` lays out the part of a line in the pixel span [skip, skip + clip); glyphs that start left of skip are dropped whole (the blitter has no left clip), so the leading glyph pops out instead of sliding out. The 128-glyph limit stays: a window never holds more, so names of any length scroll. A list with `UI_LIST_MARQUEE` scrolls the selected row's cut name after `marquee_delay` frames, a pixel every 2 frames, through two extra slots flipped by map in VBlank.
- **Layout patches:** `{view id, node id, field, value}`, at most 16 a theme, fields X, Y, W, H, ANCHOR, HIDDEN, INK, PAPER (closed set; others are ignored); the last match wins. Rectangles and HIDDEN apply at push, INK and PAPER when drawn.
- **Theme fields** (`struct ui_theme`, for T14's theme.ini): `name`; `colour[17]` = BG, PANEL, TEXT, DIM, ACCENT, ACCENT_TEXT, BORDER, TRACK, SHADOW, SELECTION, SELECTION_TEXT, ICON0-5; fonts `body`, `heading`; `row_h` (16/32), `pad` (text inset), `modal_dim` and `idle_dim` (BLDY 0-16), `fade_frames`, `slide` (px a dialog slides up from), `marquee_delay`; `input` (an `InputTiming`); `patch_count`, `patches[16]`. Palette indices are roles (0 transparent, 1 BG ... 9 SHADOW, 10-15 icons); retheming is a palette load, nothing redraws. Built-ins: `ui_theme_dark` (default) and `ui_theme_light`; seven accents (Blue, Teal, Green, Orange, Red, Purple, Pink) replace ACCENT and SELECTION. `ui_fade(colour, to, frames)` tweens a fade factor through `palette_fade` into `gfx_pal_faded`.
- **Dialogs:** a view with `UI_VIEW_MODAL` slides up by `slide` px on a spring and darkens the views under it with the blend registers (`modal_dim`). Panels have flat, outlined and rounded styles; outlined and rounded panels use the PANEL and BORDER roles.
- **DIM:** settings slot 27 (`assress_dim`, `source/ez_define.h`): idle minutes, 1-60; anything else, the erased slot included, is off (the default). It is read with `Read_SET_info` like the other settings, and the existing settings writers copy every slot below `assress_max`, so it persists through them; nothing new writes kernel NOR, and T10 adds the setting's row. After the idle time the screen darkens over a second (BLDY `idle_dim`, all layers); a key brightens it at once and does nothing else.
- **Demo:** the test kernel with L held runs `tests/kernel/ui_demo.c` instead of T4's text demo (removed): a list of 1000 synthetic items, a scroll bar, a progress bar, a count label, a dialog, a grid with icons, theme and accent switching through a fade, and DIM after 20 s. `tests/shots.py` runs a scenario on the test kernel when it has a `#! kernel test` line: `ui-list`, `ui-dialog` and `ui-theme` (every frame of the scroll, the dialog's slide and the fade hashed).
- **Cycle figures** (emulator, WAITCNT_MENU, worst frame of each): a scroll frame that draws a row 47,000 cycles, the frame of a page key with the label, bar and selection 100,832 (`ui-list-scroll`); a page change 202,369; switching screens 235,243; opening the dialog 133,625; a grid row 73,670. A whole page drawn while hidden takes about 330,000 cycles, so hidden drawing stops at 180,000 cycles into a frame (`UI_DRAW_BUDGET`) and goes on the next. A list row costs about 35,000 cycles: clearing 2,700, the model's fetch, the detail column, and the name (layout about 8,000, blit about 10,000).
- **T5 nits fixed:** the spring's settle check is in 64 bits; motions check the value range before taking a slot (an out-of-range value logs an assert naming it and returns `MOTION_NONE`); `palette_fade` rounds halves away from zero, so fades to white and black are symmetric; releasing a direction restarts the schedule of the ones still held, as the contract says; motion.h notes that `MOTION_TARGET_CALL` setters get 16.16 values.
- **Also:** `text_layout` and `text_width` handle printable ASCII inline (a small speed-up); `RGB()` in `source/ez_define.h` parenthesises its arguments (an analyzer finding that the new include made count twice).
- **Held L/R (contestable, affects the feel):** a held L or R pages every 8 frames, and the list scrolls at its top speed of a row a frame, so it moves a page in those 8 frames: no faster than a held d-pad at full speed, and the selected row is off screen for most of each page until the scroll reaches it. Jumping instead would be a page change, a blank frame each page.
- **Screens and stacking rules:** a pop and a push in one handler replace the view (the pop goes first). A view pushed after a pop waits to clear and draw its maps until regs without the popped view are committed, since its VRAM may be the popped view's. A view still being drawn doesn't take a plane from the view under it. `ui_push` refuses a list without a plane to itself and a third resident list, readably.
- **The demo runs on the emulated cart** (L and SELECT held, beside T7's SELECT-only cover demo), without the unit tests, which crash under the cart model.
- **Review (code reviewer and adversarial tester, one round):** fixed a pop then push in one handler (it pushed, then popped the new view, and dispatch could walk reused nodes); new views drawing into VRAM the popped view still showed; `ui_fade` leaking a motion slot per fade from 0; a pop clearing other lists' page-change hides (a list stuck hiding); rows of the previous folder left in the ring map after a reset to a shorter list; staged map rows overwritten by a later, overlapping stage (a table of staged spans now merges them, and a label flip or marquee step waits while its last copy is queued); hidden lists still showing; keys during a page change that spans frames leaving two rows selected (the tester's held wrap from 1000 to 1); a hide asked for between frames read as committed; a list setting the scroll of a plane a higher view shows; patched inks above 15; and a key that woke DIM repeating afterwards.
- **Not done:** cover images in the image widget (covers are sprites: the UI would build OAM each frame and run `cover_init`/`cover_update` per screen; the first screen with covers, v0.4 or T9, adds it); sprite highlights; the theme setting's row (T10). `ui_show` on a parent doesn't hide its children.

### T7 Assets (ticket)

- **PSRAM page (deviation):** the cover cache lives in page 0, the page the kernel always leaves selected, from `0x08C00000` (+4 MB; 304 KB: a 16 KB staging area and 32 slots of 9 KB). The doc's "SetPSRampage once per batch" still holds (`psram_begin` before each write batch), but nothing ever switches away, so nothing has to switch back, and a launch that patches page 0 directly (`GBApatch_Cleanrom` on `PSRAMBase_S98`) can never find another page selected. The first 4 MB of page 0 are left for T9's name index. `budget_psram_bytes` is now the cache's size.
- **Route:** SD, 4 KB a step through the stage into PSRAM staging (the cart hides PSRAM in SD mode, so `f_read` can't write there); one step decodes with SWI 11h into the stage and DMAs it to the entry's PSRAM slot (16-bit DMA at `WAITCNT_BIOS`, in 1 KB pieces); the VBlank queue copies PSRAM to sprite VRAM at `WAITCNT_MENU`, two covers a frame at most. SWI 12h isn't used, but `tools/asset.py` never emits distance-1 matches, so the data suits it.
- **Staging (ownership rule):** asset jobs borrow `READCACHE_STAGE` (the first 32 KB of `pReadCache`, listed in its owner map in `source/ez_define.h`) for one step at a time and keep nothing there between steps (`source/engine/stage.h`). That lets it overlap the other owners, which all work within one call and run no jobs; one that ever keeps data there across frames that run jobs must stop the asset jobs first (`cover_shutdown`).
- **Format:** `TAS1` assets (`source/engine/asset.h`): a 16-byte header, a raw BGR555 palette, then LZ77 tiles in 1D sprite order; at most 32x32 tiles per side, 8 KB of decoded tiles and a 16 KB file. `tools/asset.py encode` converts a PNG without colour reduction (T15 adds it). Where cover files live and how ids map to them stays v0.4's: the client passes a `cover_locate_fn` (SD path or ROM asset).
- **8bpp covers share one palette (hardware):** 8bpp sprites can't pick a palette bank, so the streamer gives 8bpp covers none; covers shown together must share the 256-colour sprite palette, which the screen loads (`cover_load_palette8`). 4bpp covers get a bank each, tagged by cache entry and shared by slots showing the same cover. v0.4 picks; the demo uses 4bpp.
- **Cache:** 32 entries keyed by a u32 id (v0.4: a path hash). Eviction takes the furthest entry (unwanted first, then wanted-but-not-loaded, failed, loaded), never a pinned (shown) or loading one; a failed cover isn't retried until evicted. One loader job serves the queue, nearest first, and ends when nothing is wanted, so frames go idle.
- **Engine additions:** `RES_NOLOG` and `res_unref` (allocations outside the view log, so streaming churn doesn't fill it with gaps), and VRAM queue tickets (`gfx_queue_ticket`, `gfx_queue_done`) so a slot is shown only once its upload has landed.
- **Testing:** the test kernel under the emulated cart crashes in the NOR unit tests, which assume no cart model. So the asset tests that need PSRAM and the card run alone when SELECT is held at power-on (`tests/assets.sh`, on a fresh cart), skip themselves in `tests/kernel.sh`, and always run on hardware (Diagnostics). The demo (`tests/kernel/cover_demo.c`) runs after them and has a golden scenario (`tests/shots/cover-demo.opts`, `#! kernel test` in `tests/shots.py`).
- **Cycles (emulator):** a 64x64 4bpp cover's decode step 38,607 (LZ77 about 31,000, PSRAM write about 7,400); its PSRAM to VRAM copy 3,427; a slide frame of the demo 18,615. mGBA times the BIOS's LZ77 its own way, so the cart's figures are T8's. A decode step is one LZ77 cover, as the contract says: an 8 KB cover may take half a frame, so T6 should start jobs early enough in the frame.
- **Memory:** about 1.2 KB of EWRAM (the loader with its FIL, 648 bytes; the cache table, 256; eight slots, 160; upload drains, 128): 18,912 bytes free after T16. No IWRAM (3100 free, as after T4).
- **Review fixes:** every launch path empties the cache (`Launch_now` and `Boot_NOR_game` too, so no cover job keeps a file open into `tlog_flush`); `cover_cache_invalidate` forgets without releasing (`cover_reset`), so stale handles from before an `engine_init` are never released; a slot emptied while its upload is queued keeps its tiles and pinned entry until the copy lands (drains); the asset tests reset the cover state; `psram_begin` before every PSRAM batch, the SD reader's included. The emulated cart now stops with status 77 on a PSRAM write while SD mode is on (`OMEGA_SD_PSRAM_WRITES=allow` lets it run on); compat passes with it.
- **Conductor review (T7):** approved; no risk found to the cart or to launching. Notes for later tickets:
  - The cover stage overlaps other `pReadCache` owners by design, safe only because nothing survives a job step. Moving it to the idle range would only trade that overlap for one with the cheat screen's work area.
  - Each cover is one sprite, at most 64x64, with 8 slots. A v0.4 grid of 12 covers needs more slots.
  - The `LOAD_PICK` step opens a file within one step, so large cover folders can hitch (T8 measures it).
  - Diagnostics' asset tests reset the cover state, so a screen that keeps covers must call `cover_init` again afterwards.
- **Conductor review (T6):** merged. The goldens look clean, and nothing risks the cart: DIM in settings slot 27 rides the existing settings writers only. Follow-ups go to T17, which runs alongside the ports:
  - **Page change:** the 1–2 frame blank on a page change or wrap becomes one hidden frame drawing only the visible rows, followed by a short alpha fade-in. The blank was visible as a flicker.
  - **Paging speed:** held L/R pages faster, at 2 rows a frame with one more row slot.
  - **Marquee:** partly visible glyphs are drawn at both edges and the strips cleared, so nothing pops, and the marquee scrolls at 1 px a frame.
  - **Row cost:** cut it (P1 `row_entries`, P2 one-pass detail column, P3 per-draw lookups, P5 visible rows first).
  - **Capacity and theme data:** raise the node cap and arena for v0.4 metadata screens, move the marquee timings into the theme, and make the scroll bar's track visible.
- **Plane convention for ports (conductor):** plane 0 holds overlay and dialog text, plane 1 the main list, plane 2 the chrome and panels, and plane 3 a second list or a list inside a dialog. Ports use designated initialisers in `ui_spec`.
- **Not done (logged):** moving `text_layout` to IWRAM would save about 20% per row but needs about 500 B of IWRAM, which isn't free, so it's skipped. A row whose data arrives later can still tear for one frame (rare and barely visible).
