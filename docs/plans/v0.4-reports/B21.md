## What changed

- **`just names-update SD_PATH`** (`tools/names_db.py`, standard library only):
  - Downloads the four No-Intro dats from libretro-database's `metadat/no-intro`, one request each, into the git-ignored `dist/dats`. Later runs use the cache. `--refresh` downloads again, `--offline` never downloads, `--dats DIR` uses another folder.
  - Writes `SD_PATH/torii/names.db`.
  - Also computes the CRC32 of every game on the card (by extension, outside the folders the kernel hides, at most 8 folders deep) and writes `SD_PATH/torii/crc.txt` (`--no-crc` skips this). Games whose path and size crc.txt already has are not read again.
  - The help text and README state the licence: libretro-database is CC BY-SA 4.0, the data comes from No-Intro, and the dats are downloaded on the user's machine and never bundled.
- **Kernel, hardware-free** (`source/namesdb.c/.h`, host-tested):
  - The names.db format and its binary search by CRC per console and by GBA game code.
  - The CRC cache: a hash table in PSRAM over records and a path pool.
  - crc.txt line parsing and formatting.
  - `names_db_name`: the CRC first, also in the other Game Boy table (a `.gb` file that is a GBC game, or the reverse), then the GBA game code.
- **Kernel, on the cart** (`source/names_store.c`):
  - **Loading.** names.db and crc.txt load into PSRAM in steps at the start of the library walk, once after each boot or game (new walk phase `W_NAMESDB`).
  - **The walk.** It checks every game's record against its file: a size or date change drops the record, and a record without a date takes the file's date. The database name goes to B4's CRC slot in `gamename_display`, so the index sort key uses the shown name.
  - **Rebuilds.** At its end the walk hashes `names_identity()`: which game got which name. New names therefore rebuild the index through B3's walk hash. `LIBRARY_VERSION` is unchanged, because the key function didn't change, and a card without names.db hashes nothing new.
  - **Identify library.** A background job (paused like the library walk), used for Settings' Identify library (`names_identify`) and, after each boot, for the games on Recent that have no CRC yet.
  - **crc.txt writes.** In steps through its own FIL, in B5's safe-file format and copy order. Every 256 new CRCs, when Identify ends, once the keys have rested 120 frames, and before a launch (from `library_before_launch`).
  - `names_lookup(path, size, console)` gives screens (B13) the name.
- **`crc32.c`**: the table moved to EWRAM and the loop works a word at a time: 17 cycles a byte at the menu's wait states instead of 39 (66 at the BIOS's). Every CRC user gains, for example the library walk's hash.
- **`safefile_scan_feed`**: works a line at a time with `memchr`. This is B5's file; behaviour is unchanged and its host tests pass.
- **Settings model**: new row `SET_IDENTIFY` "Identify library" ("Looks up each game in names.db.") in the Library section, with action `SET_ACTION_IDENTIFY`. B16 draws it and calls `names_identify()`. Nothing dispatches row actions yet, Rescan included.
- **PSRAM page 0**:
  - 5 MB: names.db (up to 1.75 MB).
  - 6.75 MB: the CRC cache (768 KB).
  - 7.5–8 MB: still reserved.
- **`library_records()`**: added to `library.h`.

## File formats

**`/torii/names.db`** (binary, little-endian, read in place from PSRAM):

- A 64-byte header:
  - Magic `TNDB`, version 1, header size, file size, CRC32 of the body.
  - The dats' version (`2026.10.07`, at most 15 characters plus NUL).
  - The entry count per console (GBA, GBC, GB, NES), the code count, the pool size, and the CRC32 of the header.
- Then, per console, `{u32 crc32, u32 name offset}` sorted by CRC. NES CRCs include the iNES header, as the dats count it.
- Then `{u32 game code (its 4 ASCII bytes as a little-endian word), u32 name offset}` sorted by code. Each code names the first retail game the dat lists for it: Beta, Proto, Demo, Sample, Kiosk, Pirate, Unl and Debug dumps lose to a retail game even when the dat lists them first.
- Then the pool: full No-Intro names, UTF-8, NUL-ended, padded to 4 with NULs. The kernel checks the header and its CRC, the size, and that the pool ends in NUL. The tables' order isn't checked: a bad order only makes lookups miss.
- **Size from today's dats (2026.10.07): 761,280 bytes (743 KB).**
  - GBA 3,503, GBC 2,433, GB 2,115 and NES 13,286 CRCs.
  - 2,756 GBA codes.
  - 568 KB of names, with identical names stored once (each NES game appears headered and unheadered).
  - Loading it takes about 1 ms per KB emulated, in the background.

**`/torii/crc.txt`** (a B5 safe file: `crc.txt` plus `crc.txt.bak`, each ending in `#crc32 xxxxxxxx`):

```
# Torii's CRC cache: CRC32, GBA game code, size, date, path
5D5C613E	AWRE	4096	5A3C7B20	/GBA/Wars.gba
3EE94D12	-	1234	-	/NES/Odd.nes
```

- Fields are tab-separated: CRC32 (8 hex digits, or `-`), GBA code (4 characters 0-9 A-Z, or `-`), size, FatFs date and time (`fdate << 16 | ftime` as 8 hex digits, or `-` when written on a PC: the next walk takes the file's), and the path from the root. The path is the rest of the line.
- An entry counts only while its file keeps that size, and that date once one is known.
- The kernel writes back only records it saw on the card at the last complete walk, so deleted games fall out.
- It holds up to 4,608 records with 640 KB of paths. Over that, or over 1 MB, the kernel doesn't write the file back, so the PC's lines aren't lost; the tool warns.

### Identify time for 1,000 games (emulated)

- **The bench:** `tests/names_db.sh bench` on the test kernel, 1,000 games of 32 KB (31.25 MB) in 10 folders. Identify (foreground loop) took 70.9 s, and writing crc.txt took 5.0 s, so **75.9 s in all**.
- **Per MB:** that is about 2.2 s per MB in the emulator: about 1.05 s of CRC (17 cycles a byte) and the rest the emulated SD. The per-game overhead (stat, open) is small.
- **On a real cart:** SD reads run at about 1,710 KB/s, so expect about 1.6 s per MB in the foreground. The background job gets at most half of each frame and pauses while keys move, so it takes at least twice that.
- **For a typical library:** 1,000 GBA games averaging 8 MB would take about 4 hours foreground and 8 or more in the background. That is why names-update computes the CRCs on the PC: the same 8 GB from a USB card reader takes minutes, and games already in crc.txt are skipped.

## Deviations

- **The launch computes no CRC.** The decisions assumed the launch reads the whole ROM anyway. It doesn't for GBA games: an SD launch hands the cart's FPGA the FAT cluster list and the cart copies the ROM into PSRAM itself (`progress_cart_copy`), so the CPU never sees the bytes. A CRC costs 17 cycles a byte at best from ROM code (39 with the old table); an IWRAM routine with an IWRAM table would be 9 cycles a byte but needs 1 KB of IWRAM data.
  - Measured, that adds about 1 s per MB to every first launch: +4 s on a 4 MB game, +32 s on a 32 MB one.
  - Instead, the launch is free. After the next boot, a background pass computes the CRCs of the games on Recent (the ones just played) that lack one, then names them and rebuilds the index.
  - The emulator and GB/NES paths (`LoadEMU2PSRAM`) do pass the bytes through `pReadCache`, but a GBC game would still add 1–4 s, so they use the same after-boot pass.
  - No IWRAM code was added.
- **names-update also computes the card's CRCs** (into crc.txt), not only names.db. Without that, a large library would need hours of Identify on the cart before names show (see the timing).
- **The CRC cache key** is path + size + date as the ticket says, but a record written on a PC has no date (the PC can't reliably compute FAT's local time). The first walk takes the file's date.
- **Screens look a name up by path and size** (`names_lookup`), because the index records have no date. The walk drops stale records, so this stays consistent.
- **The cache isn't stored "with B5's safefile" module:** it uses B5's format and copy order, but reads and writes in steps through its own FIL. B5's one-call API held the menu for seconds on a big cache, since SD writes run at about 200 KB/s.

## Decisions the user may want to contest

- `just names-update` writes crc.txt by default (`--no-crc` to skip). It reads every game on the card once, then only new or changed ones.
- **The name chain:**
  - The other Game Boy table counts too: a `.gb` file named from the GBC dat, or the reverse.
  - A GBA CRC miss falls back to the game code, so a romhack shows its base game's No-Intro name unless it has a custom name.
  - A game code names the first retail game the dat lists (not a Beta or Proto).
  - The No-Intro name goes through B4's cleaner, so tags are dropped: "Legend of Zelda, The - The Minish Cap (USA)" shows as "The Legend of Zelda - The Minish Cap".
  - Two games with the same CRC name show the same name: B4's dedupe applies only to cleaned file names.
- **Played games get names after the next boot**, in the background (a few seconds per MB on the cart), not during the launch.
- **Identify library** runs in the background, pauses while keys move, covers load or the library walks, and stops at a launch: choose it again to resume, which skips what already has a CRC. It sorts the index again every 32 new names and writes crc.txt every 256 CRCs.
- **Limits:** 4,608 cache records and 640 KB of paths; crc.txt up to 1 MB; names.db up to 1.75 MB.
- **Paths:** crc.txt keeps only library games, so games in hidden folders are never identified. Paths match without ASCII case.
- A read-only or broken crc.txt logs one error per boot and isn't written again that session.

## Bugs

- **(B16 to wire) Nothing dispatches `settings_row.action` yet** (Rescan neither): Identify library is reachable only from tests until the Settings page lands.
- **Loading a large crc.txt is slow in total:** 3,000 records take about 6 s of background after each boot (emulated), in steps of 512 bytes (under about 100k cycles each). Most of it is about 15k cycles a record to hash and store its path in PSRAM. The index from the last build shows meanwhile; only the walk waits.
- **A write step of 2 KB** can take about 10 ms on a real cart (200 KB/s), as the library index's writes already do. It runs only after the keys have rested for 120 frames.
- **Before a launch, unsaved cache changes are written synchronously** before the loading card shows: typically milliseconds, about 0.5 s for 1,000 records on a real cart. To reproduce: change a game's date on a PC, then launch within 2 s of the boot.
- **A read-only `crc.txt`** (attribute set on a PC) can't be written: the kernel logs `can't write /torii/crc.txt: open` once per boot. `.bak` holds the new data but the reader prefers the valid main copy, so dates are re-adopted and Recent re-identified each boot.
- **No-Intro names render however the font draws them:** names with odd characters weren't screenshotted. There is no game list until B13.
