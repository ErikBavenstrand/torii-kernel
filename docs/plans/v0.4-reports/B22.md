## What changed

- **Art format** (`source/engine/asset.h`): assets are now raw tiles, "TAS2": a 16-byte header, a BGR555 palette, then the tiles in row order (a BG map's order). The GBA copies them as they are; nothing decodes them. TAS1's LZ77 is gone from the format, `tools/asset.py` and the tests: nothing read it any more.
  - Box art is a TAS2 asset of 10x10 4bpp tiles (80x80) with 16 palette entries, 3,248 bytes. Colour 0 stays unused, since it is transparent on a BG.
- **Card layout and lookup** (`source/artkey.c`, hardware-free; `source/boxart.c`). The first that exists wins:
  1. `/torii/art/custom/<file name>.bin`: custom art by the game's file name, extension included ("Foo (USA).gba.bin").
  2. `/torii/art/<CRC32>.bin`: 8 hex digits.
  3. `/torii/art/<GBA game code>.bin`: 4 characters.
  4. The placeholder.

  Names match without ASCII case. The CRC and the code come from B21's CRC cache (new `names_ids()`). It works without names.db.
- **No SD access for lookups.** A background job lists `/torii/art` and `/torii/art/custom` once per boot (and after anything takes PSRAM over) into a hash set of ids in PSRAM at 7.5 MB: the set takes 64 KB (up to 8,192 files) of the 128 KB region `PSRAM_ART_BASE` reserves, and the wanted covers' file names 768 bytes after it. Static asserts keep the region inside the PSRAM window.
  - A game without art costs nothing on the card. Only a file the set holds is opened.
  - The listing waits for the keys to rest, a transition to end, no view opening or modal view (menu, dialog) up, and the library to finish building or sorting an index. The boot's hash-only check walk doesn't hold it back.
  - A card without `/torii/art` costs one `f_opendir`.
- **Cover cache, reconciled with B2** (`source/engine/cover.c` rewritten; covercache.c kept):
  - The sprite slots, drains and LZ77 decoding are gone. Covers go to BG, where B2's placeholder already was: the list page's 80x80 image node (now untagged, so its tiles are its own). The new `ui_image_show()` queues a copy of a cover's tiles straight from PSRAM into that node's tiles and loads its palette into its bank. Showing the placeholder copies `art_box_tiles` back.
  - 64 entries of 3,264 bytes from PSRAM 4 MB (204 KB). A static assert keeps the cache below the Favourites order at 4.5 MB.
  - The loader job reads each file straight into its entry's slot, in two steps: open, then read.
  - It pauses (starts no new cover and ends) while `library_walking()` or while a view opens or a modal view is up. `library_walking()` is a new query: the index loading, a walk that builds an index, or its sort. The boot's hash-only check walk, a walk only due and a write don't count, so covers load beside the check walk. A cover it has started finishes first, and the walk keeps waiting on `cover_loading()`, so the two can't deadlock.
  - A shown cover's entry stays pinned until its VRAM copy lands.
- **In the list with art** (`games.c`, small hooks: `boxart_open` in `games_enter`, `boxart_select` in `show_facts`, `boxart_poll` in `games_poll`):
  - When the cursor reaches a row, its cover shows at once if it is cached, even during a held scroll. Otherwise the placeholder shows in the console's colour.
  - After the cursor has rested 8 frames, the row's cover loads, then the rows just above and below.
  - Every 30 frames the resting row's lookup is checked again, so CRCs that load or are identified later bring its cover.
  - Covers stay cached across visits to the page.
- **Settings:** the new row **Box art** (On/Off, default On, slot 34) sits in Look, under Game view, in both game views, as mockups #18/#19 show it. With it Off the box is always the placeholder and the card's art is never read.
- **`just art-add ROM_OR_FILE_NAME IMAGE SD_PATH`** (`tools/art.py`, Pillow 13.0.0 pinned) writes `SD_PATH/torii/art/custom/<file name>.bin`. It reads any PNG or JPEG (EXIF orientation, transparency on white), then:
  - crops to a square (`--align`: by default the top of a tall picture, where box art has its title, and the centre of a wide one);
  - scales down with Lanczos and rounds to the GBA's 15-bit levels;
  - picks 15 colours (median cut refined by k-means, then each colour moved to its pixels' mode or mean, with freed slots going to the worst-served colour);
  - dithers with a serpentine Floyd–Steinberg at ¾ strength, in integers, so it is deterministic. Flat areas match a palette colour exactly and stay clean.

  Other details:
  - `--preview PNG` writes the result at 3x.
  - `art.py convert IMAGE OUT.bin` is the bare converter, for B23.
  - A ROM path that exists (the card's file) gives its name byte for byte, as the card lists it; a typed name is normalised to NFC.
  - It refuses a game name over the kernel's 255 bytes, and an art name over FAT's 255 UTF-16 characters, with a message.
  - The kernel's cover paths take 512 bytes (`COVER_PATH_MAX`), so any game name's custom art path fits (static assert).
  - The help says box art is the publishers' and isn't to be published.
- **Engine and pReadCache bookkeeping:** new owner `READCACHE_BOXART` (1 KB, within a call) in `ez_define.h`; the stage owner's text updated. The PSRAM map in `psram.h` gains the 7.5 MB art region.

## Deviations

- **The cover cache moved from sprites to BG, and the asset format from LZ77 to raw tiles (TAS1 → TAS2).** That deletes the sprite-slot streamer and its demo: covers sit where B2's placeholder was, and the GBA decodes nothing.
- **Matched art by GBA game code is `/torii/art/<CODE>.bin`.** The decisions named only the CRC file. B23 can write code files when it matches by code.
- **Game info doesn't show the cover.** Its six lines (keys 72 px, values 136 px) fill the card's width, and an 80x80 box would cut the folder and save-type lines. The conductor allowed this ("if it fits").
- **The game code comes only from crc.txt.** The ROM header isn't opened for it, since that would mean a directory search in the game's folder for each row. So code art needs crc.txt (names-update writes it, and the kernel's Recent pass and Identify add to it).
- **B18 (rename)** should call `boxart_forget()` after renaming a custom art file, so the listing is made again.

## Decisions the user may want to contest

- **Which cover wins:** custom by file name, then CRC, then GBA game code. Two copies of a game in different folders share custom art, since it goes by file name.
- **Custom art's name** is the game's whole file name plus ".bin": "Pokemon Prism.gbc.bin".
- **Timing:** covers load after the cursor rests 8 frames (`BOXART_REST`), then the rows directly above and below (`BOXART_AHEAD` 1). A cover already cached shows at once during scrolling. Covers appear without a fade. Covers wait while the library builds or sorts an index (a new card, a changed one, Rescan), not during the boot's check walk.
- **The Box art row** shows in both game views (as the mockup), default On. Turning it Off makes the box always the placeholder.
- **The converter's defaults:**
  - the top of a tall picture is kept;
  - 15 colours plus the transparent one;
  - dithering at ¾ strength;
  - transparency becomes white.
- **Limits:** 8,192 art files listed (more are left out with a logged error); 64 covers cached (about 204 KB).
- **A broken art file** logs a kernel error once per load attempt and shows the placeholder.
- **Settings' Last place on a row after Game view moves one row on an existing card.** The row ids after Game view shifted by one, because the boot position stores the row's id.
- **Covers don't load while the game popup or another menu is up**, nor while a page opens; they load once it closes.

## Bugs

- **Palette before tiles.** `ui_image_show` loads the palette at the next commit, while the tiles go through the VRAM queue. If that queue holds more than one VBlank's worth (16 KB), the new palette can show on the old tiles for one frame. At rest the queue is near empty, so it shouldn't happen. Not seen.
- **A cover finishing while the screen is dimmed by a palette fade** would load its colours into the unfaded buffer only. DIM itself uses brightness, so this needs a palette fade under way at that moment. Not seen.
- **An art folder with a few thousand files** costs one directory search per cover opened (`f_open`). It is spread over a loader step, but on a card of 4,000 art files a step could take several milliseconds; frames stay whole because jobs get only half a frame. Measured only with small folders in the emulator. A cart test with a big folder is worth doing (release checklist, B20).
- **A failed `job_start` for the listing** (all 8 job slots busy) is retried every frame and logs each time. Not seen.
