## What changed

- **`source/library.c`/`.h`, hardware-free.** The extension table (`library_console_of`; `Check_file_type` now calls it), the sort key, and the index image: header, records, sorted order, folder table and string pool. Also the builder, a sort done a few comparisons at a time, queries (n-th game of a console, path, find, counts) and in-place updates (`lib_forget`, `lib_rename`).
- **`source/library_scan.c`, the kernel side.** It is one state machine, stepped by a job between frames, or in a loop at boot and before a launch.
  - **Boot** (`library_boot`): reads the headers of `/torii/library.idx` and `/torii/library.bak` and loads the newest valid one into PSRAM. If its CRC fails, it tries the other. With no index, or another card's (volume serial), it scans and writes before the menu, with a progress dialog once that takes more than half a second.
  - **Menu job** (`library_poll`): walks the card with `f_readdir_sub` only. It hashes game names, sizes and dates, folder names, the `/SAVER` names, `/torii/names.txt` and the volume serial.
  - **Rebuild:** only when the hash differs does a second walk build a new index in the other slot, sorted by the name each game shows (its custom name from `names.txt`, else B4's cleaned name). The index then switches (`library_generation()` changes) and a job writes it.
  - **Two files:** each write replaces the older of the two, with the next generation number. A power cut while writing leaves the newer one whole, and nothing is renamed (R2).
  - **Launch** (`library_before_launch`, at the start of `Game_boot` and `Boot_NOR_game`): finishes a pending write (with a progress bar), then forgets the index. The menu reloads it after a failed launch, and the next boot reloads it after a game.
- **API:** `library_count`, `library_game`, `library_name`, `library_size`, `library_flags`, `library_path`, `library_find`, `library_total_files`, `library_truncated`, `library_games_seen`, `library_forget`, `library_renamed`, `library_changed` (after a write to `names.txt`), `library_rescan`, `library_ready`, `library_busy`, `library_generation`.
- **PSRAM page 0** (`engine/psram.h`, on B5's map):

  | From | Holds |
  | --- | --- |
  | 0 | SD list names, 832 KB |
  | 0.81 MB | 192 KB of walk scratch: save hash table, sort buffer, a copy of `names.txt` (up to 128 KB) |
  | 1 MB | two 1.25 MB slots, up to `PSRAM_LIBRARY_END = PSRAM_USERDATA_BASE` (B5's, 3.5 MB), asserted |
  | 4 MB | covers |

- **`f_readdir_sub` in the vendored FatFs** (`source/ff15/ff.c`, marked "Torii"): reads an entry and, when it is a folder, opens it from the entry just read, as `f_opendir` would but without a path lookup. A walk over a folder of N sub-folders no longer scans it again for each one. This fixes the wide-folder walk found by the adversarial tester.
- **`gamename.c` sped up (B4's code, the same results):**
  - a cheap check before trying articles;
  - inline byte checks instead of a `memcmp` per byte;
  - the final separator and space pass only when an article moved;
  - `memcpy` in rule 1;
  - names.txt comparisons fold case only where bytes differ;
  - an already sorted names.txt skips the heap sort.
- **`library_sort_key` ASCII path:** plain ASCII no longer calls the UTF-8 decoder.
- **`cover_loading()`** in `engine/cover.c`, so the walk waits while covers load.
- **The SD list (`lists.c`) hides the root `torii` folder.**

### File format (`/torii/library.idx` and `/torii/library.bak`, little-endian, version 2)

| Section | Size | Contents |
| --- | --- | --- |
| header | 64 B | magic `TLIB`, version u16 (2), header size u16 (64), record size u16 (16), flags u16 (bit 0: truncated), record count u16, folder count u16, games per console u16 x 8 (GBA, GBC, GB, NES, 4 spare), total files u32, pool bytes u32, walk hash u32, volume serial u32, body CRC32 u32, games seen u32, generation u32, header CRC32 u32 |
| records | 16 B each | folder u16, flags u16 (bits 0-3 console, bit 4 has save, bit 5 gone), size u32, name u32 (bits 0-23 pool offset of the file name, bits 24-31 half the distance to its sort key), key prefix u32 (first 4 key bytes, big-endian) |
| order | u16 each, padded to 4 | record numbers sorted by console, then by the name shown: each console's games are one A-Z run |
| folders | u32 each | pool offset of each folder's path (`/` for the root) |
| pool | padded to 4 | NUL-ended strings on halfword boundaries: file name then sort key per game, and folder paths |

- **Which file the boot loads:** the valid file with the higher generation. A file whose header is blank, from a cut write, is no index.
- **Bump `LIBRARY_VERSION`** when the layout, the sort key or B4's cleaning changes. `test_library_pinned_keys` (host) pins sample keys and fails until the version is bumped and the keys are updated.
- **Reading it on a PC:** `tests/library_idx.py FILE...` reads the newest valid of the files given.

### Sort key (R3)

- The key comes from the name shown: a custom name, else B4's cleaned name.
- ASCII and Latin-1 letters are case- and accent-folded.
- Each run of digits sorts by value. Other UTF-8 sorts after z.
- Ties go by raw file name, then folder path.

### Measured walk times (emulated)

- **Speed of emulated SD:** reads ~336 KB/s (the cart measured 1,710 KB/s) and writes ~40 KB/s, so I/O is overstated several times. CPU parts take the same time as on a cart.

| Card | First-scan walk | Total build with sort | Write | Later boots: load | Later boots: background check |
| --- | --- | --- | --- | --- | --- |
| 1,000 games, 42-char names | 2.1 s (was 3.2 s) | 2.5 s | 100 KB in 2.3 s | 0.3 s | 2.1 s wall |
| 4,097 games, 42-char names | 8.8 s (was 13.2 s) | 10.9 s | 422 KB in 9.4 s | 1.3 s | 8.6 s wall |
| 2,050 root folders, one game each | 2.9 s (was 84 s) | | | 0.46 s | 3.6 s (was 96 s) |
| 1,000 games with 1,000 custom names | 3.4 s | | | | |

- **Per-game CPU in a build:** `gamename_clean` is 7.8k cycles (0.47 ms; it was 22.9k), the key 3.0k (was 4.5k), and the whole build about 14k (0.84 ms; it was about 30k).
- **Parsing a 1,000-line `names.txt`:** 0.26 s if sorted (as the kernel writes it), 0.82 s if not. It is one step, so a background rebuild with that many custom names stalls the menu once by that long. With a realistic few dozen names it takes milliseconds.

## Deviations

- **R1 in two passes.** The background walk only hashes; a second walk builds when the hash differs. The first scan's write runs at boot.
- **The fingerprint** covers game names, sizes and dates, folder names (not dates), `/SAVER` names and `names.txt`. Non-game files never trigger a rewrite.
- **Unreadable folders:** a folder FatFs reports as damaged is skipped and logged, and the walk goes on. Any other read error stops the walk and keeps the old index.
- **Depth cap:** folders deeper than 8 levels aren't indexed.
- **Vendored FatFs gains `f_readdir_sub`.**

## Decisions the user may want to contest

- **First scan dialog:** shows only when the scan takes over half a second: "Library" / "Looking for games on the card", status "N games found".
- **"Saving the game list" before a launch:** if the index changed and hasn't been written yet (writes wait for 2 s without keys), a launch first shows "Library" / "Saving the game list" with a bar, before the launch's own loading card (up to ~2 s for 4,096 games on a cart).
- **Extensions match exactly:** `.sgb` files and names without a dot (`romgba`) no longer count as games and no longer launch. The old suffix match accepted them.
- **Unreadable boot sector:** if the boot sector can't be read, the volume serial counts as 0. A card whose boot-sector read fails only sometimes rebuilds at those boots, and so does an index from another card.
- **Two index files on the card:** `/torii/library.idx` and `/torii/library.bak`.
- **Nearly full cards:** the index isn't written while the card would keep less than 1 MB free (when FatFs knows the free space). Such a card scans at every boot.
- **What "total files" counts:** what the SD card page shows (B4's rule).
- **Save dots:** follow the launch path's save names (`.sav` for GBA, `.esv` for emulated games).
- **Custom names:** they sort their game; a big `names.txt` (over 128 KB) is ignored for sorting.

## Bugs

- **Menu changes don't update the index yet.** `library_forget`, `library_renamed`, `library_changed` and `library_rescan` have no callers. Menu deletes, renames and custom names show after the next boot's walk until B13, B14, B16 and B18 call them.
- **The walk can't save the index on some cards.** With `/torii` as a file, or a write-protected card, every boot logs the error and scans again.
- **`names.txt` parsing is one step.** A background rebuild with a large `names.txt` (hundreds of lines) stalls the menu once for up to a few tenths of a second. Slicing `gamename_custom_parse` is for v0.4.2.

## Changelog

- **Library index (main commit):**
  - The boot loads the game index (`/torii/library.idx` and `.bak`, written in turn; every game by extension, up to 4,096, A-Z per console by the name shown) into PSRAM, or builds it with a progress dialog once slow.
  - A background walk rebuilds and rewrites it only when games, saves, custom names or the card change (R1).
  - The SD list hides Torii's folder.
  - Name cleaning is about three times faster, and a FatFs helper opens sub-folders without a path lookup.
- **Library names (names.txt commit):** custom names are read through the safe file (B5).
