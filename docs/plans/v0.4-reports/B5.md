## Branch and commits

## What changed

- **Safe writes** (`source/safefile.c`, hardware-free checks in `source/safefile_scan.c`), reusable for B4's `names.txt` and later files: R2's two copies. `safefile_write(path, max, fill, ctx)` writes the whole text to one copy and closes it, then the other; each copy ends in `#crc32 xxxxxxxx` (zlib CRC32 of everything before that line). No rename, no delete. `safefile_open/line/close` read the copy that holds up. `struct safefile_lines` turns a "line n" callback into the fill callback.
- **The lists** (`source/userdata.h`): hardware-free parsing, edits, the cap, the unix-time conversion and the "played ago" formatter in `source/userdata.c`; the kernel's store in `source/userdata_store.c`. Both lists live in PSRAM page 0 (`PSRAM_USERDATA_BASE`, the last 512 KB before the cover cache; `NAMES_BYTES` shrinks to 3.5 MB), are read from the card on first use (`userdata_load()` reads both up front) and again after a launch (`userdata_invalidate()` in `Game_boot` after the Recent hook, and in `Launch_now`). RAM work borrows `pReadCache` at `READCACHE_USERDATA` (0x8000, 32 KB; listed in `ez_define.h`).
- **API** for B10/B13/B14/B18: `userdata_recent_count/path/time`, `userdata_recent_add(_file)`, `userdata_forget(_file)`, `userdata_forget_nor`, `userdata_rename`, `userdata_boot_get/set`, `userdata_flush`, `userdata_fav_count/path/has/set`, `userdata_now`, `userdata_ago_text`.
- `Recently_play_*`, `p_recently_play`, `RECENT_NOR`, `RECENT_LEN` are gone; the launch paths and `screens/lists.c` (calls only) use the new module. A launch adds the game (SD path or `NOR:name`) with the clock's time; a file missing at launch, a file deleted from the SD list, a NOR game deleted and FORMAT ALL take entries off both lists.
- The v0.3 list `/SAVER/Recently play.txt` (with its `NOR:` entries) is read while `recent.txt` doesn't exist; the first write of Recent takes it over and deletes it.
- Emulator: `OMEGA_POWER_CUT=sd:write:N` cuts the power before the Nth SD write command (`emu/patches`, documented in `omega-de-hardware.md`).

## File formats

`/torii/recent.txt` (newest first, at most `USERDATA_RECENT_MAX` = 32 games):

```
@boot gba 3
1800000000	/GBA/Advance Wars.gba
0	NOR:Golden Sun.gba
#crc32 1a2b3c4d
```

- `@boot <item> <row>`: written first, only once a place has been set. `<item>` is a word of letters, digits, `-` and `_` (up to 15; B10 picks the names), `<row>` a decimal number.
- `<unix time><TAB><path>`: the time is the cart clock's reading as if UTC (0 when the clock reads before 2026-10-01, T4). The time may be left out (a bare path, as the v0.3 list has).
- A path is an SD path from `/` (folder under 256 bytes, name up to 255, no control characters: what the launch path can open) or `NOR:` and a game NOR name (up to 99 bytes).

`/torii/favorites.txt`: one path per line, in byte order of the paths (sorted on load if edited by hand); the store holds 4,096 favourites in about 480 KB of PSRAM.

Both: a copy over 64 KB (Recent) or 2 MB (favourites) counts as missing; a UTF-8 BOM is skipped; blank lines and lines starting with `#` are skipped; lines that don't parse, paths the launch path can't take, duplicates and games past the cap are dropped (logged). CRLF and surrounding blanks are fine. Each file has a second copy `NAME.bak` with the same text.

Reading: `NAME` if its CRC line holds; else `NAME` as edited by hand when it is text (no NUL) and not empty (FatFs writes a size only at close, so a cut write leaves `NAME` empty, and a write that fails empties its copy); else `NAME.bak` if it holds; else empty. A read that fails (a card error, not a missing or broken copy) marks the list: it is shown as read but never written back until a later read is whole, so a short read can't become permanent in both copies. Writing: the copy a reader takes now is written last (`NAME.bak` first, unless `NAME` is the broken one), so one whole copy is always on the card.

## Deviations

- R2's two copies replace the ticket's tmp+rename, as the conductor directed. Refinement: the copy a reader would take now is written last, so when `NAME` is the broken one, `NAME` is written first.
- Migration is lazy: the v0.3 list is read while `recent.txt` doesn't exist, and the first write of Recent (a launch, a forget) takes it over and deletes it. So the boot never writes to the card. Every write of Recent deletes the v0.3 list if it is still there (a power cut can leave it beside a new `recent.txt`).
- The ticket's "power cut between write and rename" test is a power cut before each SD write of a save (`OMEGA_POWER_CUT=sd:write:N`, new in the emulated cart).
- A copy larger than a size cap counts as missing (64 KB for Recent, 2 MB for favourites): a huge hand-edited file stalled the menu for minutes.
- A copy whose write fails (a full card) is truncated to empty, so it can't outrank the other copy as a hand edit.
- Conductor review: a read that fails marks its list unwritable until a clean read (`safefile_failed()`; tested with a name FatFs refuses, as the emulated cart can't fail reads, and `Read_SD_sectors` reports no errors today), and only an empty `NAME` counts as a cut write (R2's prefix backstop dropped, so lines trimmed by hand stay trimmed).
- Until B14 hides it, the v0.3 SD list shows the `torii` folder once a launch has written Recent (it already did with LOGGING on). I adjusted the test key sequences instead of adding a hide rule to `lists.c`, which B10 deletes.
- `userdata_load()` exists for B10's boot and the pages, but nothing calls it yet (the v0.3 Recent screen reads the list before it draws).
- B4's `struct gamename_io` (whole-file read and write for `names.txt`) has no adapter yet, as B4 left it: the adapter is `safefile_open` plus `safefile_line` joined with newlines for read, and `safefile_write` with a fill that copies from the buffer for write.

## Decisions the user may want to contest

- **Favourites order in the file:** byte order of the paths, so lookups are a binary search. The pages sort by the shown name (R3) themselves.
- **Hand edits:** a file without a valid CRC line is the user's edit and wins (trimming lines off its end included), unless it is empty: an empty `NAME` is what a cut write leaves, so `.bak` is read. So to clear a list on a PC, delete both `NAME` and `NAME.bak`, or leave a comment line: emptying `NAME`, or deleting only `NAME`, brings `.bak` back. A file edited with its old CRC line still in it reads as a hand edit too.
- **"Played ago":** under a minute "just now"; "5m ago"; "2h ago"; 24-48 h "yesterday"; 2-6 days "3 days"; 7-13 days "1 week"; then "2 weeks" to "4 weeks"; 30-59 days "1 month"; "2 months" to "12 months"; "1 year"; "2 years". Nothing for time 0 or a time after now.
- **Unset clock (T4):** "before the build date" is a fixed date in the source, 2026-10-01 (`USERDATA_CLOCK_FROM`), because the build is reproducible and carries no date. Times are the cart clock read as UTC.
- **Forgetting:** a file missing at launch or deleted from the SD list leaves both Recent and the favourites; a NOR game deleted, and FORMAT ALL, take NOR games off both.
- **`@boot` line:** written only once a place is set (B10); `<item>` is a word of letters, digits, `-` and `_`, up to 15 characters.
- **Favourites are capped at 4,096** (about 480 KB of paths in PSRAM), although the decisions say favourites have no cap: adding past it fails. The cap is the library's 4,096 games.
- **A game goes on Recent before its load succeeds**, as in v0.3: the launch hook runs after the save is handled and before the ROM is loaded, so a launch that fails later (a cart error during the copy) still lists the game.
- **Card errors:** a list whose read failed is shown as read but not written back until a later read (after the next launch, or the next boot) is whole.
- **Limits:** Recent 32 (T3); lines with paths the launch path can't open (folder over 255 bytes, name over 255, NOR names over 99, control characters) are dropped when read. A UTF-8 BOM is skipped.
- **PSRAM:** the lists take the last 512 KB of the 0-4 MB "names and library index" region (`PSRAM_USERDATA_BASE` = 3.5 MB); `NAMES_BYTES` ends there. B3 lays out the rest of 0-4 MB; it must stay below `PSRAM_USERDATA_BASE`.
