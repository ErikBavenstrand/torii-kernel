## What changed

- **E4 / T13:** `UI_GRID` is gone. `ui_list_config` loses `cell_w`, so its fields are now `{model, row_h, flags, detail_w}`. Every initialiser was updated. The UI demo's grid screen, its SELECT switch and the grid tests and goldens were removed.
- **E14:** `frame_measure` keeps up to 4 names a frame (`FRAME_MEASURES`), each logged once. `frame_measure_drop` takes a name off when a new measurement replaces it in the same frame. `ui_run.c` now always measures `ui-transition` and `ui-dialog-motion`, alongside a screen's own name.
- **E13:** `ui_list_autoscroll` emits `UI_EV_CURSOR` for each move. The event is sent from the update with `ui_dispatching` set, and `ui_frame` applies the pops it asks for after `update_all`.
- **E2:** `ui_fade` works out only the banks `gfx_pal_load` has written (`gfx_pal_used`, the new `palette_fade_banks`), not all 512 colours. The UI demo's fade frame went from 58.8k to 27.9k cycles. BLDY wasn't used: it would fight the other blends (DIM, dialog dims, page fades), which take one register set at a time.
- **E12:** a row cache keyed by item, in the new `source/ui/rowcache.c`/`.h`, hardware-free with host tests.
  - Size: `ROW_CACHE_BYTES` 24 KB in EWRAM, up to 32 rows.
  - Allocation: space is a ring, and a lookup is O(1) through a hint table.
  - Format: a row is stored column after column, its lines in order. Any row height or column stride copies in or out, so B9's 14 px pixel-pitch canvas can use it unchanged (`row_cache_copy_out` with a stride).
  - Filling: a list copies its rows in one per frame while it rests (`keep_resting`, in the update). Scrolling therefore never pays for the cache.
  - Use: a row scrolled back to is copied from the cache (about 4.4k cycles for a 16 px row) instead of drawn (13k–24k).
  - Invalidation: `ui_list_refresh` drops the refreshed items, `ui_list_reset` takes a new owner, and a theme change clears the cache. Rows on screen after a theme change are kept again only once they have been redrawn.
- **E1:** a page change fades the old page out first. This uses the theme's new `page_fade_out` (4 frames, an alpha blend like the fade-in). The plane is hidden only at the end of the fade, then the new page fades in. The list no longer blanks abruptly.
  - It falls back to the old instant hide when a darken blend is on (DIM, a dialog's dim) or another plane is fading.
  - A cursor move during the fade retargets the page.
- **E3:** while the old page fades out, the new page's rows are drawn ahead into the row cache within the new `UI_PAGE_BUDGET` (140k cycles into the frame). The hidden frame then only copies them in.
  - The hidden page draw uses the same budget, and its row estimate is now the largest lately (decaying), so one long name doesn't overrun it.
  - A screen's first draw (a view not shown yet) keeps `UI_DRAW_BUDGET` 250k, so screens still come in on the same frame as before (see Decisions).

## Deviations

- **E3 budget:** the page change got its own budget (`UI_PAGE_BUDGET` 140k). The hidden first draw of a new screen stays at `UI_DRAW_BUDGET` 250k. With one lower budget for both, every screen entrance (`tr-tab`, `tr-menu`, `sd-tab-held`) came in a frame later. Screen-open frames still peak at about 213k (`lists-screen`), as before. B19's zoom draws its page during the motion, so it should use `UI_PAGE_BUDGET` (or less) there.
- **E12 research:** `research-v04-rows.md` judged a row cache "doesn't pay" for B9's cheaper 14 px rows. The ticket asked for one, so here is how it is shaped to pay:
  - it never stores during scrolling (stores happen only at rest, in idle frames; an earlier store-on-eviction version raised held-scroll frames by about 15k and was dropped);
  - it is what lets E3 draw the next page ahead.
  - With 14 px rows costing about 7–8k (B9's estimate), a hit (about 3.5k) saves less than today. If B9 finds the cache isn't worth its 24 KB, `ROW_CACHE_BYTES` can shrink to one page (about 14 KB).
- **No theme.ini key** for `page_fade_out`: B1 removed `theme.ini`.

## Decisions the user may want to contest

- **Page change look:** the old page now fades out over 4 frames (`page_fade_out`), then the new one fades in over 4 (`page_fade`). Before, it vanished for a frame and faded in. A page change therefore takes about 3 frames longer to land: the page shows about 9 frames after the key instead of about 6. The keys and A pressed meanwhile still act on the new page. Setting `page_fade_out = 0` in `ui_theme.c` restores the old behaviour.
- **The cache takes 24 KB of EWRAM** (about 52 KB stay free). It holds about 12 full-width 16 px rows: one page plus a few.
- **The UI demo** (test kernel only) lost its grid screen and SELECT key.
- **A page change under DIM or a dialog's dim** has no fade-out: the old page vanishes at once, as before B7, because the screen's single blend is already taken. If such a blend starts during a fade-out, the old page is hidden in that same frame.
- **Palette fades (`ui_fade`) apply only to loaded banks** (`gfx_pal_load`). Code that writes palette RAM another way isn't faded.

## Notes for B9

- `ui_list.c`'s cache calls assume tile-aligned slots: `cached_row` passes `rt * 8` lines, `keep_resting` and `render_row` pass a stride equal to the line count, and `ROW_COPY` is the cost estimate for a 16 px copy. With 14 px rows in a pixel-pitch canvas, pass the canvas's column stride and the row's line offset (`row_cache_copy_out`/`_in` take both) and re-time `ROW_COPY`.
- A copy whose length per column isn't a multiple of 8 words (any 14-line row) doesn't use `CpuFastSet`: it falls back to a word-by-word loop in `rowcache.c`, which is safe for VRAM (no byte stores) but slower. A 14-line strided copy is 28 runs of 14 words; consider DMA3 per column if it shows in the figures.

## Bugs

- **Diagnostics' line list** (`source/diag.c`, `lines_fetch`): a line that falls out of the `DIAG_LINES` window returns "" but isn't refreshed. If the list scrolled back that far, a cached row would show the old text. The cursor always follows the latest line, so this can't show today. Pre-existing contract gap; fix it when the reading view replaces it (B17).
- **E13 handlers** must not push or pop views: the event comes from the update phase, and `ui_core_push` applies waiting pops at once. Documented in `ui.h`. No current handler does either (the only autoscroll user, Diagnostics' renderer demo, has no handler).
- **A screen's first draw** can still peak near 260k cycles in the UI demo's first frame (unmeasured: before `screen ready`). This is the same as before B7 (`UI_DRAW_BUDGET` plus the nodes drawn after the list).
