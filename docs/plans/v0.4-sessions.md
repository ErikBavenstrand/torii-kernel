# v0.4 ticket sessions

How each v0.4 ticket session works. The conductor (the session that plans and merges) starts one session per ticket in `v0.4-decisions.md`; this file is the protocol every ticket session follows.

## Branches

- `v0.4` is the integration branch. Every ticket session works in its own worktree cut from `v0.4` and never pushes to `v0.4` or `main`: the conductor reviews and merges.
- Push your branch to `origin` when you report, so the conductor can merge it.
- Before reporting, rebase onto the latest `origin/v0.4` (`git fetch origin && git rebase origin/v0.4`), resolve conflicts, and re-run `just check`.
- Commit unsigned: `git -c commit.gpgsign=false commit ...` (1Password signing is unavailable). Never change git config. No attribution lines in commits.

## Setup in a new worktree

- Copy the user's test games: `cp -cR /Users/erik.bavenstrand/Code/torii-kernel/roms ./roms` (an APFS clone, instant). `roms/` is git-ignored; never commit it.
- The first `just test` fetches and builds the emulator (about 25 s).
- Containers only see paths under the home folder; your worktree is inside the repo, so that holds.

## Work

1. Read `CLAUDE.md`, `docs/plans/v0.4-decisions.md` (the contract: Scope through Library and data, the ticket interview record, "Rules for every ticket", and your ticket), `docs/design/v0.4/spec.md` and the mockups your ticket names, and the research files the brief names (`docs/research/v0.4/`).
2. Discover: read the code your ticket touches and the tickets that merged before you (`git log origin/v0.4`, `docs/plans/v0.4-reports/`).
3. Implement. Performance first (60 fps, `tests/perf/budget.txt`), look values in one place, clean from the start (delete what you replace), strings in `source/lang.c`.
4. Test: the tests your ticket lists, then `just format` and `just check`. Every `just test` line must start with `PASS` (or `SKIP (waiting for Bn)` where the rules allow it). For anything visible, look at the PNGs.
5. Review: launch review agents (a code reviewer; add an adversarial tester for launching, saves, the cart model, patching or NOR writes). Give them your test and compat results and a time budget. Fix what they find, re-check, and repeat until you are completely happy. A ticket isn't done while a reviewer's real finding stands.
6. Report (below), rebase, push, and end with the report as your final message.

## Mockup tickets (B16 Settings, B18 keyboard)

Draw the mockup first (Pillow at 240x160 in the Galmuri fonts, light and dark, like `docs/design/v0.4/pages-*.png`), commit it to `docs/design/v0.4/`, then build it. The user is not available to approve it during the build: pick the design you think is best, and list it in your report as a decision for the user to review.

## Report

Write `docs/plans/v0.4-reports/Bn.md` (committed on your branch) with these sections, and paste the same as your final message:

- **Branch and commits:** the branch name and its commits.
- **What changed:** a few lines.
- **Tests:** what ran and passed (`just check` tiers, compat runs, new tests, goldens added or re-recorded, frame-cycle figures for new screens and motions, `just size` and `just stack` figures if they moved).
- **Deviations:** anything that differs from `v0.4-decisions.md` or the spec, and why.
- **Decisions the user may want to contest:** choices you made that change what the user sees, feels or stores: behaviour, look, motion, limits, file formats, keys, texts. Not internal details (register choices, names of functions).
- **Bugs:** bugs you found and didn't fix (new or pre-existing), each with where and how to reproduce.
- **Changelog:** the `CHANGELOG.md` lines for your `source/` changes, with the final short hashes (after your last rebase). Do not edit `CHANGELOG.md` yourself: parallel branches would all conflict there. The conductor adds these lines when it merges.

## Safety (unchanged from CLAUDE.md)

- Kernel NOR is written only through `Save_info`, within `[0x780000, 0x7C0000)`. Nothing but Diagnostics' read-only loader check sets ROM page `0x8000`. Any new path that writes kernel NOR goes into `tests/loader_safety.sh`.
- The user's library, `~/Documents/Files/Nintendo`, is theirs: never write to it or use its saves.
- `just compat` only (not `--all`, which B20 runs): the colima VM is shared by several sessions at once.
